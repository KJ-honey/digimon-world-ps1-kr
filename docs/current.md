# 현재 상태

기준일: 2026-09-27. 기록 ID: `recovery-001`.

## 사용자 목표와 완료 조건

사용자는 기존 한국어패치판을 기반으로 (1) 부족한 폰트 확장, (2) 주인공과 디지몬 이름의
조합형 한글 입력, (3) 일본어 원문 대조를 통한 오역·맞춤법·미번역 개선을 요청했다.
특정 누락 장면은 기억하지 못한다고 답했다. BIOS는 프로젝트 `bios/`에 제공했다.
범위를 줄이거나 어휘를 제한하기로 한 결정은 없다.

완료에는 전체 대상 문자열의 글자 공급, 편집·확정·대사 삽입·다른 화면 재표시·저장과 재로드,
원문 대조 검수, 원본으로부터 재현되는 제품 빌드, 실제 게임의 회귀 검증이 필요하다.
이름 입력 UI 배열·최대 길이·기존 세이브 호환 정책은 아직 선택하지 않았다.

**가장 큰 미해결 조건:** 이름 화면에서 만든 한글의 정체성과 글꼴을 저장·재로드 및 모든
이름 표시 경로까지 유지하는 것. 입력 화면만 바꾸거나 일부 이름만 보이는 결과로 완료하지 않는다.

## 기준 입력과 보존

| 입력 | SHA-256 |
| --- | --- |
| 일본어판 | `a99ce1cf5c3524b866603fe29f412c956131e7a2d48807e2508d9304ba6f20cd` |
| 기존 한국어판 | `12346b169b67fed618df8262e701781f42db1cdde7c459bb92190a24371f54d9` |

두 원본은 읽기 전용으로 열었고 변경하지 않았다. 각 381,160,416 bytes,
162,058개의 2,352-byte Mode 2 sector다. 153,762 Form 1, 8,296 Form 2.
원본과 패치판의 ISO9660 디렉터리 및 파일 LBA·길이는 동일하다. 부트 실행 파일은 `SLPS_017.97`.
고유 게임 리비전의 외부 명칭은 아직 판정하지 않았으며 위 해시만 지원 기준이다.

기존 패치 복구: `tools/recover_baseline.py`로 xdelta3 3.2.0 패치를 만들고 실제 ISO로 복원했다.
복원 ISO 전체 해시는 기존 한국어판과 일치한다. 영상·sector 보호 필드도 그대로 포함한다.
`work/recovery/verification.json`에 도구 버전·해시가 있다. 새 폰트/입력 기능은 포함하지 않는다.

## 확인된 구조

증거는 `tools/survey.py`, `tools/recover_assets.py`로 재생성한다.

### 매체와 변경 자원

818개 파일 중 53개 파일 extent에 변경 sector가 있다. 45,613개 sector,
84,877,935개 raw byte가 다르며 파일 extent 밖 변경은 없다.

- `SLPS_017.97`: 글꼴과 UI 문자열 등. 현재 확인한 글꼴 렌더러는 두 판에서 바이트 동일.
- `SCN/DG.SCN`: 대사 스크립트 후보. 파일 크기 692,224 bytes.
- `SCN/MAPHEAD.SCN`: 변경된 텍스트/스크립트 영역; 내부 구조는 미해석.
- `SHOP_REL.BIN`: 이름 입력 선택 문자 및 라벨. 변경 범위 `0x7A90..0x7CDF`.
- BTL/FISH/KAR/STD/VS 모듈에도 변경이 있다. 각 문자열 경계와 소비자는 미확정.
- CARD, TIM, MAP 및 4개 STR 영상에도 변경이 있다. 대사/폰트만 재삽입해서 기존 그래픽·영상 변경을 잃지 않도록 한다.

Form 1의 변경 파일과 명시한 보조 파일을 양쪽 모두 추출하고 모든 출력 바이트를 raw payload 좌표와 비교했다.
영상은 mixed/Form 2이므로 2,048-byte 읽기로 잘못 평탄화하지 않고 raw extent 해시와 변경 sector 수만 기록했다.
이는 자원 추출 검증이며 ISO 재조립 검증과는 다르다. 전체 재현은 별도 xdelta 왕복으로 검증했다.

### 폰트와 코드 → 픽셀 경로

| 항목 | 확인 값 |
| --- | --- |
| EXE load address / payload | `0x80090800` / 파일 `0x800`부터 |
| 파일 → RAM | 이 EXE 범위에 한해 `RAM = offset + 0x80090000` |
| 문자 코드 배열 | 파일 `0x98578`, RAM `0x80128578`, 991개의 little-endian u16 |
| 마지막 검색 항목 | 파일 `0x98D36`, RAM `0x80128D36`; 디스크에서는 0, 런타임에 요청 코드로 덮어쓰는 sentinel |
| 비트맵 시작 | 파일 `0x98D38`, RAM `0x80128D38` |
| 글꼴 한 칸 | 12×11, 22 bytes, 행마다 little-endian u16, bit15→bit4, 0이 잉크 |
| 변경 | 991칸 중 919칸 변경; 코드 배열은 동일 |
| 기본 대체 글꼴 | 파일 `0x9E262`에 22 bytes; 대각선이 든 상자, 두 판 동일. 총 저장 비트맵은 992칸 |
| 소비 함수 | `0x800A575C`, 파일 `0x1575C` |

`work/recovered/font-renderer.asm`에서 다음을 확인했다.

1. 입력 16-bit 값을 byte-swap하여 코드 비교에 사용한다. 디스크 문자열의 SJIS형 byte 순서와 대응한다.
2. `0x8140`은 글꼴 조회 없이 빠진다(공백).
3. `0x800A57F8`에서 sentinel에 요청 코드를 써넣고 배열을 선형 검색한다.
4. 찾은 인덱스에 22를 곱해 비트맵 위치를 계산한다.
5. 11행, 행당 12개의 1bpp bit를 색상 nibble로 바꾼다. 21개의 72-byte 버퍼를 순환하는 코드가 있다.
6. `0x800A5B24`에서 변환 버퍼 및 3×11 word 직사각형을 함수 `0x8009486C`에 전달한다.
   GPU 업로드 함수의 정확한 정체와 버퍼 수명은 런타임으로 아직 검증하지 않았다.

991이라는 수는 저장된 코드/글꼴 수다. 모든 문자를 VRAM에 고정 배치하는 991칸 한계라고 해석하면 안 된다.
전체 글자 집합, RAM 상주 용량, 변환 버퍼와 화면 수명은 별도 예산이다.

없는 코드는 인덱스 991 sentinel과 일치하여 마지막 22-byte 대체 글꼴을 읽는다.
처음에는 코드에 대응되는 991칸만을 글꼴 범위로 생각했으나, 후속 픽셀 확인에서
마지막 대체 글꼴(대각선 상자)을 확인했다. 따라서 배열 밖 임의 데이터 읽기로 해석하지 않는다.
이 정적 분석은 미등록 코드의 동작이며 현재 한국어판에서 실제 발생한다는 증거는 아니다.
현재 7,857쌍의 한국어 대사 후보에는 문자표 밖 코드가 없고, 991칸에 완전히 빈 비트맵도 없다.
일본어 후보에는 `8E5A`, `915F`가 각 1회 나오며 VM 경계 검증 전에는 원본 결함으로 단정하지 않는다.

### 대사 복원 범위

DG 헤더의 첫 226개 u32는 225개 2,048-byte 정렬 시작점과 EOF 경계값이다.
첫 시작점 `0x800`, EOF `0xA9000`. 뒤에는 경로 문자열이 있으므로 헤더 전체를 포인터로 오인하면 안 된다.
두 판의 이 할당 경계는 동일하다. 스크립트 실행·섹션·분기 의미는 아직 조사 중이다.

`1A00` 뒤의 2-byte 문자열/제어 후보와 `0000` 끝을 검색하여 양쪽 동일 위치 7,857쌍을 얻었다.
한쪽만 발견된 후보는 없다. 원문/기존 번역 raw bytes, 후보 ID, 파일 오프셋, 할당 script index를 보존한다.
**이 수는 실제 번역 작업량 또는 전체 추출 완료 수가 아니다.** 실행되지 않는 데이터, VM 인자 오인,
메뉴/아이템/이름/다른 모듈의 누락 범위가 남아 있다.

정적 대조 HTML은 직접 추출한 양쪽 글꼴로 문자열을 그린다. 화면 크기나 줄 배치의 게임 검증은 아니다.
OCR 874개 제안을 별도 보존했다. 직접 검수 기록은 별도 파일에 있으며 원본 OCR 제안을
번역 복원본이나 빌드 입력으로 사용하지 않는다.
사용자가 제공한 [googlefonts/gulim 소스](https://github.com/googlefonts/gulim/tree/main/sources)의
Gulim 2.21 TTC (commit `012723a8d5b6a6dc920330f26d165422c3014fd6`), face 0,
12px 내장 비트맵을 12×11, 원점 (0,0), 1-bit로 그려 비교했다.
변경 글리프 919개 중 910개는 한글 11,172자 중 하나와 픽셀 전체가 정확히 일치하고,
모두 유일하다. 그중 564개만 OCR 제안과 같아 OCR 오인식이 상당수 확인됐다.
나머지 9개는 픽셀 불일치이며 3개는 최근접 굴림 글자와 단 1픽셀 차이지만,
6개는 60픽셀 이상 차이로 굴림 한글 후보라고 단정할 수 없다.
비교 결과와 폰트 해시는 `work/review/glyph-matches.json`에 기록했다.
로컬 검수 도구 `tools/glyph_review.py`는 1픽셀 차이의 근접 후보 3개를 기본 목록으로
보여주고 후보 선택/직접 입력 후 단일 저장 버튼으로 결정한다. 나머지 6개는 별도 목록에서
확인하며 근거 없는 굴림 후보를 제시하지 않는다. 기존 수동 검수 251건은 보존했다.
그중 54건이 픽셀 완전 일치 결과와 충돌하며 도구에서 자동 결과를 우선 표시한다.
이전 수동 기록과 새 결정은 원본 `glyphs.json`을 바꾸지 않고
`work/review/glyph-review.json`에 남는다. 원본 SHA-256이 달라지면 이전 결과를 적용하지 않는다.
폰트 대조는 정적 픽셀 일치 증거이며 런타임 표시나 모든 코드 소비자의 검증은 아니다.
검수 결과를 제품 빌드나 번역에 연결하는 절차는 아직 없다.

### 이름 입력

`SHOP_REL.BIN`의 `0x7A90` 이후에 원문 이름 라벨 및 가나 선택 배열이 있고
기존 한국어판에서는 해당 코드들이 한글 선택 코드로 바뀌었다.
선택 문자열 사이에 포인터/데이터가 섞여 있으므로 전체 구간을 연속 문자열로 재삽입하면 안 된다.
현대 한글 입력의 범위, 조합 상태와 삭제, 이름 필드 길이, 세이브 구조, 다른 소비자는 미확정이다.

개발용 정렬 수정판의 실제 새 게임에서 두 이름 입력 화면까지 도달했다.
RAM `0x80085000..0x800869FF`가 `SHOP_REL.BIN` 파일 `0x4800..0x61FF`와 일치하여
이 구간 overlay base `0x80080800`을 확인했다.
첫 선택 글자 `마`는 bytes `8B A6`이며 편집 버퍼 `0x80167BCC`에 기록된다.
write breakpoint가 문자 두 byte writer `0x80084C3C`, `0x80084C68`과
terminator writer `0x80084C84`를 포착했다. 저장은 2-byte 문자 + 1-byte NUL 종료다.
6글자 뒤에는 종료 항목으로 넘어가며, 다음 circle 입력으로 이름 확정 단계가 진행됐다.
주인공 `마`와 디지몬 `마마마마마마`가 각각 확인 대사에 재표시되는 것을 확인했다.
주인공 이름은 `0x8013A924`에도 복사되었고, 디지몬 이름의 복사 후보는 `0x8016B0EC`다.
이 실험은 메모리카드를 쓰지 않는 경로이므로 게임 세이브·재로드는 아직 검증하지 않았다.

기존 `취소` 항목은 현재 커서 위치를 NUL로 만든 뒤 커서를 한 칸 뒤로 옮기는 동작이다.
따라서 첫 선택에서 마지막 글자가 즉시 사라지지 않을 수 있다. 조합형 삭제 설계에서
이 동작을 일반적인 backspace로 오인하지 않아야 한다.

### 실행 환경과 문자열 정렬 결함

사용자 제공 `bios/SCPH5500.BIN`(SHA-256
`9c0421858e217805f4abe18698afea8d5aa36ff0727eb8484944e00eb5e7eadb`)을 사용한다.
Mednafen 1.32.1 + emucap adapter `df23142`를 로컬 빌드했다. 시스템 GNU ar가 만든
Mach-O archive 링크 실패는 `/usr/bin/ar`, `/usr/bin/ranlib`로 재생성하여 해결했다.
실행 환경 해시와 개입 기록은 `work/runtime/environment.json`에 보존한다.

기존 한국어 ISO에서 BIOS 부팅, 한국어 자막 오프닝, 한글 타이틀 로고를 관찰했다.
RAM의 글꼴 22 bytes도 추출 EXE와 일치했다. 이는 이름 입력·저장 검증을 의미하지 않는다.
`video.frameskip 0` 설정 전후 모두 전환 중 검은 캡처가 있었으므로 frameskip을 원인으로 확정하지 않는다.

타이틀 이후 한국어판의 CPU 예외: `EPC=0x800A5B78`, `BadVAddr=0x80139AA5`.
이 주소의 명령은 `lhu v0,0(v0)`로, 홀수 주소의 16-bit 읽기에서 주소 오류를 낸다.
EXE 파일 `0xAA35C`에 있는 포인터가 일본어판 `0x80139AA0`에서
한국어판 `0x80139AA5`로 바뀌어 있다. 인접 포인터에도 홀수 주소가 있다.
`work/runtime/black-diagnostic/`의 RAM·레지스터 덤프와 `.mcs`에 실패 상태를 보존했다.
이 결함은 글자 수 부족과 별개다. 이 시점에는 일본어판 메뉴 진입 비교가 아직 끝나지 않았다.

`tools/build.py`는 기존 한국어 ISO를 불변 입력으로 하는 **개발용 정렬 수정 실험판**을 만든다.
파일 `0x15B78..0x15B87`의 고정 4명령을 다음과 같이 바꾼다.

```asm
lbu v1,1(v0)
lbu v0,0(v0)
sll s2,v1,8
or  a0,s2,v0
```

기존 little-endian 16-bit 값을 byte load로 구성한다. 두 load delay 사이에 독립 명령이 있고,
분기·호출·스택·코드 위치는 바뀌지 않는다. 함수 내부에서 v1은 기존에도 caller-saved이며
s2는 함수 종료 시 복원된다. a0의 결과는 기존 16-bit 값과 같다.
기존 16 bytes의 정확한 일치와 Capstone 최종 디코딩을 검사한다.
348개 원본 EXE sector의 EDC/P/Q가 재생성 결과와 전부 일치했고,
수정은 LBA 148103의 코드 16 bytes와 해당 sector EDC/P/Q 범위로 제한한다.
전체 출력 diff도 이 사전 쓰기 계획에 일치하는지 검사한다.
실험판 SHA-256: `ee2ded562d66e21fe36a8cf280189c5a87771af0420778814c8174f46ed7cdb3`.
이 실험판을 savestate/RAM 변경 없이 cold boot하여 한글 메뉴, 새 게임 대사,
주인공·디지몬 이름 입력과 확인 대사 재표시까지 통과했다.
증거: `work/runtime/alignment-verification.json` 및 그 안의 화면·해시.
이 결과는 관찰한 정렬 결함의 수정 증거이며 전체 게임 회귀 통과를 뜻하지 않는다.
폰트 확장·이름 조합·번역 개선 완료본은 아니다.

폰트 확장과 조합형 이름 입력의 최종 구현 방식은 메모리·소비자 조건을 확인한 후 결정한다.
