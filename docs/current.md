### 매체와 변경 자원

818개 파일 중 53개 파일 extent에 변경 sector가 있다. 45,613개 sector,
84,877,935개 raw byte가 다르며 파일 extent 밖 변경은 없다.

- `SLPS_017.97`: 글꼴과 UI 문자열 등. 현재 확인한 글꼴 렌더러는 두 판에서 바이트 동일.
- `SCN/DG.SCN`: 대사 스크립트 후보. 파일 크기 692,224 bytes.
- `SCN/MAPHEAD.SCN`: DG 첫 할당 영역의 23,094-byte 사본이며 script 0의 실제 로드 원본.
  후속 DG 소비자 조사에서 확인했다. 아래 DG 재삽입 절차는 양쪽 사본을 함께 수정한다.
- `SHOP_REL.BIN`: 이름 입력 선택 문자 및 라벨. 변경 범위 `0x7A90..0x7CDF`.
- BTL/FISH/KAR/STD/VS 모듈에도 변경이 있다. 각 문자열 경계와 소비자는 미확정.
- CARD, TIM, MAP 및 4개 STR 영상에도 변경이 있다. 대사/폰트만 재삽입해서 기존 그래픽·영상 변경을 잃지 않도록 한다.

Form 1의 변경 파일과 명시한 보조 파일을 양쪽 모두 추출하고 모든 출력 바이트를 raw payload 좌표와 비교했다.
영상은 mixed/Form 2이므로 2,048-byte 읽기로 잘못 평탄화하지 않고 raw extent 해시와 변경 sector 수만 기록했다.
이는 자원 추출 검증이며 ISO 재조립 검증과는 다르다. 전체 재현은 별도 xdelta 왕복으로 검증했다.

### 폰트와 코드 → 픽셀 경로

| 항목 | 확인 값 |
| --- | --- |
| EXE load address / payload | `0x80090800` / 파일 `0x800`부터 |
| 파일 → RAM | 이 EXE 범위에 한해 `RAM = offset + 0x80090000` |
| 문자 코드 배열 | 파일 `0x98578`, RAM `0x80128578`, 991개의 little-endian u16 |
| 마지막 검색 항목 | 파일 `0x98D36`, RAM `0x80128D36`; 디스크에서는 0, 런타임에 요청 코드로 덮어쓰는 sentinel |
| 비트맵 시작 | 파일 `0x98D38`, RAM `0x80128D38` |
| 글꼴 한 칸 | 12×11, 22 bytes, 행마다 little-endian u16, bit15→bit4, 0이 잉크 |
| 변경 | 991칸 중 919칸 변경; 코드 배열은 동일 |
| 기본 대체 글꼴 | 파일 `0x9E262`에 22 bytes; 대각선이 든 상자, 두 판 동일. 총 저장 비트맵은 992칸 |
| 소비 함수 | `0x800A575C`, 파일 `0x1575C` |

`work/recovered/font-renderer.asm`에서 다음을 확인했다.

1. 입력 16-bit 값을 byte-swap하여 코드 비교에 사용한다. 디스크 문자열의 SJIS형 byte 순서와 대응한다.
2. `0x8140`은 글꼴 조회 없이 빠진다(공백).
3. `0x800A57F8`에서 sentinel에 요청 코드를 써넣고 배열을 선형 검색한다.
4. 찾은 인덱스에 22를 곱해 비트맵 위치를 계산한다.
5. 11행, 행당 12개의 1bpp bit를 색상 nibble로 바꾼다. 21개의 72-byte 버퍼를 순환하는 코드가 있다.
6. `0x800A5B24`에서 변환 버퍼 및 3×11 word 직사각형을 함수 `0x8009486C`에 전달한다.
   GPU 업로드 함수의 정확한 정체와 버퍼 수명은 런타임으로 아직 검증하지 않았다.

991이라는 수는 저장된 코드/글꼴 수다. 모든 문자를 VRAM에 고정 배치하는 991칸 한계라고 해석하면 안 된다.
전체 글자 집합, RAM 상주 용량, 변환 버퍼와 화면 수명은 별도 예산이다.

없는 코드는 인덱스 991 sentinel과 일치하여 마지막 22-byte 대체 글꼴을 읽는다.
처음에는 코드에 대응되는 991칸만을 글꼴 범위로 생각했으나, 후속 픽셀 확인에서
마지막 대체 글꼴(대각선 상자)을 확인했다. 따라서 배열 밖 임의 데이터 읽기로 해석하지 않는다.
이 정적 분석은 미등록 코드의 동작이며 현재 한국어판에서 실제 발생한다는 증거는 아니다.
현재 7,857쌍의 한국어 대사 후보에는 문자표 밖 코드가 없고, 991칸에 완전히 빈 비트맵도 없다.
일본어 후보에는 `8E5A`, `915F`가 각 1회 나오며 VM 경계 검증 전에는 원본 결함으로 단정하지 않는다.

### 대사 복원 범위

DG 헤더의 첫 226개 u32는 225개 2,048-byte 정렬 시작점과 EOF 경계값이다.
첫 시작점 `0x800`, EOF `0xA9000`. 뒤에는 경로 문자열이 있으므로 헤더 전체를 포인터로 오인하면 안 된다.
두 판의 이 할당 경계는 동일하다. 초기 조사에서는 실행·섹션·분기가 미확정이었다.
후속 소비자 기반 파서의 확인 범위와 남은 조건은 아래 `DG 명령 경계와 재삽입`에 기록한다.

`1A00` 뒤의 2-byte 문자열/제어 후보와 `0000` 끝을 검색하여 양쪽 동일 위치 7,857쌍을 얻었다.
한쪽만 발견된 후보는 없다. 원문/기존 번역 raw bytes, 후보 ID, 파일 오프셋, 할당 script index를 보존한다.
**이 수는 실제 번역 작업량 또는 전체 추출 완료 수가 아니다.** 실행되지 않는 데이터, VM 인자 오인,
메뉴/아이템/이름/다른 모듈의 누락 범위가 남아 있다.

정적 대조 HTML은 직접 추출한 양쪽 글꼴로 문자열을 그린다. 화면 크기나 줄 배치의 게임 검증은 아니다.
OCR 874개 제안을 별도 보존했다. 직접 검수 기록은 별도 파일에 있으며 원본 OCR 제안을
번역 복원본이나 빌드 입력으로 사용하지 않는다.
사용자가 제공한 [googlefonts/gulim 소스](https://github.com/googlefonts/gulim/tree/main/sources)의
Gulim 2.21 TTC (commit `012723a8d5b6a6dc920330f26d165422c3014fd6`), face 0,
12px 내장 비트맵을 12×11, 원점 (0,0), 1-bit로 그려 비교했다.
변경 글리프 919개 중 910개는 한글 11,172자 중 하나와 픽셀 전체가 정확히 일치하고,
모두 유일하다. 그중 564개만 OCR 제안과 같아 OCR 오인식이 상당수 확인됐다.
나머지 9개는 픽셀 불일치이며 3개는 최근접 굴림 글자와 단 1픽셀 차이지만,
6개는 60픽셀 이상 차이로 굴림 한글 후보라고 단정할 수 없다.
비교 결과와 폰트 해시는 `work/review/glyph-matches.json`에 기록했다.
로컬 검수 도구 `tools/glyph_review.py`는 1픽셀 차이의 근접 후보 3개를 기본 목록으로
보여주고 후보 선택/직접 입력 후 단일 저장 버튼으로 결정한다. 나머지 6개는 별도 목록에서
확인하며 근거 없는 굴림 후보를 제시하지 않는다. 기존 수동 검수 251건은 보존했다.
그중 54건이 픽셀 완전 일치 결과와 충돌하며 도구에서 자동 결과를 우선 표시한다.
이전 수동 기록과 새 결정은 원본 `glyphs.json`을 바꾸지 않고
`work/review/glyph-review.json`에 남는다. 원본 SHA-256이 달라지면 이전 결과를 적용하지 않는다.
폰트 대조는 정적 픽셀 일치 증거이며 런타임 표시나 모든 코드 소비자의 검증은 아니다.
검수 결과를 검색·원문 대조 자료에 연결하는 절차는 아래에 구현했다. 제품 빌드에는 아직
연결하지 않았다.

### 검수 문자표 → Unicode 복원

`python3 tools/restore_text.py`는 검수 결과를 `work/text/character-map.json`으로 정리하고,
`work/text/dialogue-candidates.jsonl` 및 한국어 검색 가능한 `work/text/review.html`을 만든다.
기존 추출 파일과 검수 기록은 보존하며 입력별 해시가 붙은 사본을 `work/text/inputs/`에 남긴다.
원본 추출 EXE의 코드·픽셀, 굴림 파일 해시와 실제 렌더링, DG 후보의 원래 위치·바이트를
검사한 뒤 출력한다. 도구는 ISO를 수정하거나 번역 문장을 자동 수정하지 않는다.

- 픽셀 일치 910칸 + 사용자가 확정한 `8DEC=뼈`, `9688=팬`, `95E2=늪`: 한글 913칸,
  서로 다른 한글은 912자다. `늪`은 `88C0`(225번)와 `95E2`(988번)에 중복되어 있다.
- 공통 기호·숫자·영문 61칸을 합쳐 991칸 중 974칸에 Unicode가 있다. 렌더러의
  `8140` 공백은 별도 항목이다. 기호의 기존 수동 결정도 보존한다.
- 나머지 17칸은 코드 정체성을 보존한다. 일부는 SJIS로 소문자·중괄호처럼 읽히지만,
  실제 픽셀은 버튼/단위 등 특수 모양이다. 일반 SJIS 디코딩으로 이 칸을 확정하지 않는다.
  굴림과 60px 이상 달랐던 6칸도 반전 기호 모양이며 DG 한국어 후보에는 사용되지 않았다.
  이것은 다른 파일에서의 미사용 증거가 아니다. 픽셀 확인: `work/review/non-hangul.png`.
- 기존 수동 검수와 정확한 픽셀 일치가 충돌한 54건은 검수 UI에서 쓰던 픽셀 일치 우선

### DG 명령 경계와 재삽입

사용자 요청에 따라 일본어 EXE의 실제 VM·텍스트 소비자를 분석하고
`tools/dg_script.py`, `dg_analyze.py`, `dg_export.py`, `dg_build.py`를 구현했다.
주소·조건·재현 명령은 [dg-script.md](dg-script.md)에 있다.
기존 `tools/build.py`의 정렬 수정 전용 동작은 유지한다.

확인된 소비자는 VM opcode fetch RAM `0x800F0780`, 섹션 탐색 `0x800F0A4C`,
텍스트 `0x800F4200`이다. 실제 opcode는 1 byte이고, `1A` handler가 다음 byte를
건너뛴다. 텍스트 `03`은 **4 bytes**, 일반 문자/다른 현재 분기는 2 bytes를 소비한다.
종료는 임의의 `0000` 검색이 아니라 `0D xx` 뒤의 zero-byte 검사와 종료쌍 소비다.
양쪽 판의 해당 소비자·jump table 바이트가 같다. `6B`는 다른 판 편집기의 인자 폭을
채택하지 않았고, 데이터처럼 보이는 후속 바이트와의 관계가 미해결이다.

script 0은 DG가 아니라 별도로 로드된 MAPHEAD RAM `0x80159784`를 사용한다.
DG 논리 `[0x800, 0x6236)`과 MAPHEAD `[0, 0x5A36)`은 두 판 각각 완전히 같다.
따라서 script 0 편집은 두 파일을 함께 갱신한다. native 소비자 `0x800FA3F8`의
섹션+index×4 조회도 확인하고 섹션 1220..1230의 154개 참조를 보존한다.
이는 native 참조 전체 조사 완료를 의미하지 않는다.

현재 확인 범위:

- 225 할당 영역, 섹션 참조 1,559개에서 출발한 명령/복합 명령 34,189개와
  텍스트 4,617개의 경계가 양쪽 판에서 같다. 명시적 참조 대상 불일치와 명령 overlap은 0.
- 기존 검색 후보 4,476개가 경계와 대응하며, 검색이 놓친 단위 141개도 확인했다.
  기존 후보 3,381개는 소비 경로 미확인이다. 한국어 미확인 payload 중 3,301개는
  확인된 단위와 같지만 중복 바이트만으로 실행 여부를 판정하지 않는다.
  실제로 DG `0x6800..0x6A5B`의 604 bytes가 할당 tail에 그대로 반복되는 사례가 있다.
- `6B`에서 멈추는 경로 4개: script 98/153/179/220, DG 논리 offset
  `0x40FB8`, `0x690E2`, `0x84E24`, `0xA489A`.
- 매매 수정 후보 `0x4240`은 현재 CFG/native catalog에서 참조가 없어 빌드가 거부한다.
  이를 dead data 또는 실제 매각 화면의 결함으로 단정하지 않는다.

전체 DG를 헤더·명령·opaque 영역으로 나눠 JSON 저장/재로딩·재조립한 결과,
**양쪽 각각 692,224 bytes / 225 영역이 원본과 동일**하다. opaque 영역은 해석 완료가
아니라 원본 보존이다. 한국어 확인 텍스트 4,617개 / payload 230,022 bytes를 Unicode
manifest로 왕복해 넣은 ISO도 기존 한국어 ISO 전체 해시와 일치했다.
증거: `work/dg/analysis/summary.json`, `work/build/dg-all-unchanged/build.json`.

기존 `dg_build.py`의 재삽입 정책은 길이·제어 위치 보존이다. 없는 글자, 모호한 중복, 제어/인자 변경·이동,
미확정 글리프 변경, 길이 차이, 중복 writer, 원본 불일치를 오류로 처리한다.
자동 공백 추가·축약·누락은 없다. 전체 참조 및 버퍼 예산이 미확정이므로 relocation은

### 대사 바이트 확장 (`dg-expand-001`)

2026-09-28, 번역 중인 메인 워크트리와 분리하여 `tools/dg_expand.py`,
`dg_bank.s`, `dg_bank_verify.py`, `dg_expand_audit.py`를 추가했다.
기존 manifest의 원문 ID/hash를 유지하면서 원문보다 긴/짧은 번역을 넣는다.
번역 문장 자동 변경은 없으며 아래 이미지는 합성 QA다. 기술·명령·한계는
[dialogue-expansion.md](dialogue-expansion.md)에 기록했다.

일반 script 버퍼는 RAM `80161784..80163783`의 8 KiB이고 바로 뒤가 VM 상태다.
단순 파일 확대/명령 이동은 채택하지 않았다. 원문 payload 첫 4 bytes에 bank descriptor를
넣고, `800F4200` wrapper가 별도 대사를 읽어 원본 소비자에 전달한 뒤 원래 continuation으로
되돌린다. 다음 opcode의 `1A` 여부 검사도 유지한다. 모든 script-relative 명령·분기·섹션·
선택지 offset은 보존하며, script 0 descriptor는 MAPHEAD와 DG 양쪽에 쓴다.

DG 초기 directory read의 8 KiB 중 원래 script 0을 중복 로드하던 영역에 helper와
2 KiB scratch를 배치한다. DG의 script 파일 offset만 일률 `+0x1800` 이동하며 RAM
배치는 그대로다. 대사당 한 sector의 bank를 붙이고 DG 전체를 raw track 뒤에 append한다.
ISO9660 DG extent/size와 PVD volume size 양쪽 endian을 갱신한다. 다른 파일의 위치와
기존 DG extent는 보존한다. 원본 대사 길이 대신 인코딩·제어 순서·64-byte 출력 행 경계를
검사한다. 기존 줄 수를 보존하며 자동 줄바꿈/페이지 추가는 아직 없다.

확인된 4,617 단위에 시험 공백 2 bytes를 추가하는 감사에서 **4,592개**가 통과했다.
25개는 `07/08/09/11/12`(hex) 동적 table 삽입의 최악 출력 길이가 미확정이라 변경 시
거부한다. `05/06` 이름은 최대 6글자, 숫자는 원본 digit loop를 예산으로 사용한다.
4,592개 모두 설치된 wrapper의 CPU 실행에서 긴 원문 소비자 대조와 출력/반환 폭이 같고,
원래 continuation·callee-saved 상태·scratch guard가 보존됐다. **CD I/O와 BIOS 문자열
서비스는 명시적 stub**이므로 이 결과를 실제 장면·streaming 검증으로 계산하지 않는다.
연속 `1A` 대사 606개를 포함해 원래 다음 opcode에 따른 textbox 상태도 대조했다.
증거: `work/build/expanded-stress/bank/cpu-verification.json`.

`work/build/expanded-qa-02/dg-expanded.cue`의 SHA-256은
`ba238d1f6e18a46b5e25cc187df1867c3d06e0847ecbeb5350912a63fc0e5d23`다.
Mednafen 1.32.1 / emucap df23142에서 콜드 부팅한 뒤 다음을 확인했다.

사용하지 않았다. 씨앗몬 복귀 이벤트와 CPU 종료 검증을 별도로 남겼다.

원문 길이 제한을 해제한 개발 기능이며 전체 대사 추출 완료나 배포 완료 주장이 아니다.

### 번역 초안 플레이 테스트 (`translation-playtest-001`, 2026-09-28)

### 대사 공백과 연출 배치 (spacing-003)

2026-09-28 현재 번역의 일반 공백은 `0F00`(6px), 전각 공백은 `8140`(12px)으로
구분했다. 둘 다 2바이트다. 쉼표·느낌표 자체는 12px를 유지한다. 원문 행 앞 들여쓰기와
연출용 열 맞춤을 전각으로 복원했다. 확인된 DG 4,617개 중 문구 2,558개를 수정했고,
쉼표·느낌표 직후 불필요 공백 1,667곳을 제거했다. 원문에 `「」` 없는 1,020개를
배치 관점에서 대조하여 440개를 수정했다. 원문 전체 의미 검수나 해당 장면 전수 플레이
완료를 뜻하지 않는다. 가격표 36행 중 스테이크 메뉴 3행은 한국어 길이 때문에 숫자 열을
원문보다 12px 오른쪽으로 함께 옮겼으며, 실제 식당 화면은 아직 확인하지 않았다.

원래 `0F00` 명령은 논리 +6px지만 업로더가 X를 4px 단위로 잘라 실제 공백이 4·8px로
교대했다. 첫 화면 41글자 중 15글자의 위치가 2px 어긋나 ‘원래 엔진 그대로 정확히 6px’
가설을 폐기했다. 사용자는 처음에는 정밀 반칸이 불필요하다고 했으나, 교대 간격을 확인한
뒤 **실제 6픽셀 고정으로 수정**하도록 결정했다. 이전 승인으로 이 요구를 무시하지 않는다.

현재는 DG 행을 스택 버퍼에 4bpp로 구성한 뒤 한 번 전송하는 렌더러를 구현했다.
행 파서·폰트 공급·색 제어·탭은 기존 코드를 호출하며, 공백 및 다음 글자의 좌표를 정확히
유지한다. 716 bytes 코드는 회수한 폰트 영역 내 EXE 논리 offset `0x9D714`
(RAM `0x8012D714`)에 있고 추가 상주 RAM은 없다. 임시 스택 1,616 bytes를 사용하며
GPU 전송 완료를 기다린 뒤 반환한다. 비DG 글리프 업로드는 원래 경로를 유지한다.

현재 테스트 CUE: `work/build/spacing-003/dg-expanded.cue`.
ISO SHA-256: `cbfe77c24d3197dd24542dbeac89025009a6d524c21145ada37ef0c75cfa0946`.
선택 4,581개 중 payload 변경 4,385개, 동일 bytes 196개다. 이전 사용자 승인 테스트판과
**동일한 36개만** 원문으로 보류하며 추가 보류는 없다. 이전 초안 보호 토큰 4,617개 전부
보존했다. 자동 테스트 62개, sector 계획/diff·재추출, 변경 4,385개 소비자 CPU 검증을
통과했다. 2,429 glyph의 정렬/반칸 뒤/인접 픽셀, 일반 업로드, ABI·스택 및 여러 행
배치를 CPU 검증했다. GPU는 stub이며 실제 화면 결과와 구분한다.

실제 게임에서 새 이미지를 state 로드·RAM 쓰기 없이 콜드 부팅하여 첫 할배몬 대사,
다음 질문, 선택지와 응답까지 진행했다. 첫 화면 41개 glyph는 **화면 X=52+논리 X**에
정확히 놓였으며 글꼴 픽셀 불일치 0개다. 전각 들여쓰기·6px 공백·색상 및 다음 대사의

`jijimon-first-003.png`, `jijimon-next-003.png`에 증거가 있다. 전체 게임·연출 장면
회귀와 저장/재로드는 통과로 보고하지 않는다. [상세 기록](dialogue-spacing.md) 참조.

- 자동 테스트 74개 통과. `dg_layout_verify.py`로 원래 MIPS 소비자와 행 렌더러를 실행하여
  10,606줄 모두 계산값과 실제 glyph/clear 좌표가 일치함을 확인했다. 동적 값은 위 상한의
  전각 글리프 fixture로 치환했고 GPU는 stub이다. 실제 이름 테이블 전수 실측·게임 화면
  및 페이지 전환 검증은 아니다. CPU 증거는 `work/line-width-168/cpu-widths.json`이다.

이번 변경은 번역문과 빌드 입력까지 반영했다. ISO 재생성·실제 게임 실행은 하지 않았다.
문구 승인 상태와 `product_eligible=false`를 유지하며, 리뷰 서버는 새 규칙으로 재시작했다.

### 두벌식 이름 입력 (`name-entry-001`, 2026-09-28)

사용자는 **두벌식 자판처럼 연속 자모 입력**을 선택했다. `tools/name_entry.c`와
`name_entry.py`를 추가하고 `dg_expand.py --expand-font --name-entry`에 통합했다.
기존 6글자/2바이트 코드/NUL 형식을 유지한다. 복합 모음·겹받침·받침의 다음 초성 이동,
조합 단위 삭제, 쌍자음 전환을 지원한다. 자모만 남거나 KS X 1001 밖 음절이면 확정을
거부한다. 부분 조합은 이름 레코드에 쓰지 않으며, 없는 글자의 대체·누락은 없다.

현재 이미지: `work/build/name-entry-final/dg-expanded.cue`.
ISO SHA-256 `fe082b33fc7bab96695aa1be89255edc2a13a87bd88381339ec17e29e282b0f7`.
`name-007`, `name-008`, `name-entry-final`의 이미지가 전체 해시 일치한다.
최신 168px 대사 4,617개 중 변경 4,424개와 Mona12 확장을 함께 포함한다.
이름 입력용 호환 자모 51칸을 더해 전체 폰트는 fallback 포함 2,481칸이다.

- SHOP RAM `[800849E0,80086504)` / SHOP 논리 `[41E0,5D04)`의 이름 전용 루틴을
  대체한다. 코드 4,528바이트. 기존 창 생성자의 callback·초기화 5곳을 연결한다.
  파일 크기/LBA/추가 상주 RAM은 바꾸지 않는다. transient 상태는 SHOP에 둔다.
- 이름 조회표 2,832바이트는 KS membership + legacy membership + 기존 glyph의
  10-bit index다. 기존 font/pixel row 뒤 여유 1,368바이트와 SHOP 대체 영역을 사용한다.
  Unicode 한글 전체에 글꼴을 추가하는 것이 아니며 지원 음절은 계속 2,350자다.
- Clang 23.1.2 / LLD 22.1.6의 MIPS I 생성, LLVM·Capstone 최종 디코딩,
  재어셈블 왕복, load/branch delay 검사 통과. Clang 기본 div-zero 검사에 생기는
  `teq`가 MIPS I 밖임을 검출했고, 상수 분모만 쓰며 그 검사를 생성하지 않게 했다.
- 최종 ISO에서 추출한 코드로 11,172개 조합 조회, 2,350자 × 6칸 = 14,100개
  실제 두벌식 키 경로, 지원 밖 8,822개 확정 거부, 복합 모음·겹받침 삭제, 길이 경계,
  모든 CPU 쓰기 범위·callee-saved·스택 보존 검사 통과.
- 결합 이미지의 폰트 2,481칸, 일반/대사 픽셀 경로 2,480개 유효 glyph,
  변경 대사 4,424개 CPU 소비 검증 통과. 기존 자동 테스트 74개 통과.
  GPU/CD/BIOS stub 여부는 각 `cpu-verification.json`에 구분한다.

Mednafen 1.32.1 / emucap df23142의 별도 세션(47940)으로 `name-007`을 콜드 부팅했다.
새 게임에서 메모리카드 슬롯 1의 빈 기록을 선택했다. 미완성 `ㄱ`과 지원 밖 `갂`의
START 확정 거부, L1 전환, `ㄱㅗㅏㄹㄱ`에서 삭제해 `괄`로 돌아오는 실제 화면을 확인했다.
주인공 `갇췄힝`, 디지몬 `달가갑사바까`를 입력·확정하여 확인 대사에 재표시했다.
주인공은 RAM `8013A924`, 디지몬은 `8016B0EC`에 정확한 코드가 복사된다.
입력 및 확인 대사의 `갇췄힝` 12×11 foreground는 생성 Mona12 glyph와 0픽셀 차이다.

두 이름 모두에서 새 glyph를 확인하려고 **같은 이미지**의 디지몬 입력 체크포인트를
로드해 디지몬을 `달가갇췄힝까`로 다시 입력했다. 이 재시험은 상태 접근 개입으로 기록한다.
직접 RAM/코드/이름 값 주입은 하지 않았다. 짧은 자동 입력 중 누락된 방향/L1은 읽은
커서·shift 상태로 확인하고 실제 패드 입력을 다시 보냈다. 입력 작업 중 별도 save_state가
일시정지시킨 한 차례의 실험도 원시 로그에 보존했다. 코드 결함 증거로 계산하지 않는다.
후속 도입부의 주인공 이름 대사 표시와 마을 진입도 확인했다.
2026-09-28 사용자가 “이제 됐어”라고 하여 여기서 검증을 중단하고 입력을 해제·에뮬레이터를 일시정지했다.
메모리카드 저장·새 프로세스 재로드와 상태 메뉴/전투 등 후속 소비자 검증은 미완료다.

재현/주소/동작은 [name-entry.md](name-entry.md), CPU 증거는
`work/build/name-entry-final/{name,font,bank,pixel-row}/cpu-verification.json`,
화면·버튼 로그·RAM·상태는 `work/name-entry/`에 있다. 번역 승인 상태는 바꾸지 않았고,
배포 가능이나 전체 게임 회귀 통과를 주장하지 않는다.

### 기존 이름 입력 조사 (이전 리비전)

`SHOP_REL.BIN`의 `0x7A90` 이후에 원문 이름 라벨 및 가나 선택 배열이 있고
기존 한국어판에서는 해당 코드들이 한글 선택 코드로 바뀌었다.
선택 문자열 사이에 포인터/데이터가 섞여 있으므로 전체 구간을 연속 문자열로 재삽입하면 안 된다.
조합형 입력으로 확정할 한글 음절은 KS X 1001 2,350자로 정해졌다. 11,172자 전체 지원은 필요 없다.
조합 상태와 중간 표시·삭제, 이름 필드 길이, 세이브 구조, 다른 소비자는 미확정이다.

개발용 정렬 수정판의 실제 새 게임에서 두 이름 입력 화면까지 도달했다.
RAM `0x80085000..0x800869FF`가 `SHOP_REL.BIN` 파일 `0x4800..0x61FF`와 일치하여
이 구간 overlay base `0x80080800`을 확인했다.
첫 선택 글자 `마`는 bytes `8B A6`이며 편집 버퍼 `0x80167BCC`에 기록된다.
write breakpoint가 문자 두 byte writer `0x80084C3C`, `0x80084C68`과
terminator writer `0x80084C84`를 포착했다. 저장은 2-byte 문자 + 1-byte NUL 종료다.
6글자 뒤에는 종료 항목으로 넘어가며, 다음 circle 입력으로 이름 확정 단계가 진행됐다.
주인공 `마`와 디지몬 `마마마마마마`가 각각 확인 대사에 재표시되는 것을 확인했다.
주인공 이름은 `0x8013A924`에도 복사되었고, 디지몬 이름의 복사 후보는 `0x8016B0EC`다.
이 실험은 메모리카드를 쓰지 않는 경로이므로 게임 세이브·재로드는 아직 검증하지 않았다.

기존 `취소` 항목은 현재 커서 위치를 NUL로 만든 뒤 커서를 한 칸 뒤로 옮기는 동작이다.
따라서 첫 선택에서 마지막 글자가 즉시 사라지지 않을 수 있다. 조합형 삭제 설계에서
이 동작을 일반적인 backspace로 오인하지 않아야 한다.

### 실행 환경과 문자열 정렬 결함

사용자 제공 `bios/SCPH5500.BIN`(SHA-256
`9c0421858e217805f4abe18698afea8d5aa36ff0727eb8484944e00eb5e7eadb`)을 사용한다.
Mednafen 1.32.1 + emucap adapter `df23142`를 로컬 빌드했다. 시스템 GNU ar가 만든
Mach-O archive 링크 실패는 `/usr/bin/ar`, `/usr/bin/ranlib`로 재생성하여 해결했다.
실행 환경 해시와 개입 기록은 `work/runtime/environment.json`에 보존한다.

기존 한국어 ISO에서 BIOS 부팅, 한국어 자막 오프닝, 한글 타이틀 로고를 관찰했다.
RAM의 글꼴 22 bytes도 추출 EXE와 일치했다. 이는 이름 입력·저장 검증을 의미하지 않는다.
`video.frameskip 0` 설정 전후 모두 전환 중 검은 캡처가 있었으므로 frameskip을 원인으로 확정하지 않는다.

타이틀 이후 한국어판의 CPU 예외: `EPC=0x800A5B78`, `BadVAddr=0x80139AA5`.
이 주소의 명령은 `lhu v0,0(v0)`로, 홀수 주소의 16-bit 읽기에서 주소 오류를 낸다.
EXE 파일 `0xAA35C`에 있는 포인터가 일본어판 `0x80139AA0`에서
한국어판 `0x80139AA5`로 바뀌어 있다. 인접 포인터에도 홀수 주소가 있다.
`work/runtime/black-diagnostic/`의 RAM·레지스터 덤프와 `.mcs`에 실패 상태를 보존했다.
이 결함은 글자 수 부족과 별개다. 이 시점에는 일본어판 메뉴 진입 비교가 아직 끝나지 않았다.

`tools/build.py`는 기존 한국어 ISO를 불변 입력으로 하는 **개발용 정렬 수정 실험판**을 만든다.
파일 `0x15B78..0x15B87`의 고정 4명령을 다음과 같이 바꾼다.

```asm
lbu v1,1(v0)
lbu v0,0(v0)
sll s2,v1,8
or  a0,s2,v0
```

기존 little-endian 16-bit 값을 byte load로 구성한다. 두 load delay 사이에 독립 명령이 있고,
분기·호출·스택·코드 위치는 바뀌지 않는다. 함수 내부에서 v1은 기존에도 caller-saved이며
s2는 함수 종료 시 복원된다. a0의 결과는 기존 16-bit 값과 같다.
기존 16 bytes의 정확한 일치와 Capstone 최종 디코딩을 검사한다.
348개 원본 EXE sector의 EDC/P/Q가 재생성 결과와 전부 일치했고,
수정은 LBA 148103의 코드 16 bytes와 해당 sector EDC/P/Q 범위로 제한한다.
전체 출력 diff도 이 사전 쓰기 계획에 일치하는지 검사한다.
실험판 SHA-256: `ee2ded562d66e21fe36a8cf280189c5a87771af0420778814c8174f46ed7cdb3`.
이 실험판을 savestate/RAM 변경 없이 cold boot하여 한글 메뉴, 새 게임 대사,
주인공·디지몬 이름 입력과 확인 대사 재표시까지 통과했다.
증거: `work/runtime/alignment-verification.json` 및 그 안의 화면·해시.
이 결과는 관찰한 정렬 결함의 수정 증거이며 전체 게임 회귀 통과를 뜻하지 않는다.
폰트 확장·이름 조합·번역 개선 완료본은 아니다.
