# 한글 2,350자 확장

2026-09-27. 사용자는 기존 선별 글자를 모두 보존하고 KS X 1001의 상용 한글
2,350자와 합집합을 만들도록 요청했다. 기존 서로 다른 한글 912자는 모두 이 집합에
포함된다. 따라서 새 한글 1,438자를 추가하여 총 2,350자를 공급한다.
기존 913개 한글 슬롯(`늪` 중복 포함), 기호 78개, 대체 글꼴 1개를 모두 보존하여
저장 글리프는 2,430칸이다. `8140` 공백은 원래의 렌더러 분기를 유지한다.

**사용자 확정(2026-09-27): 조합형 이름 입력도 KS X 1001의 2,350자만 지원하면 충분하다.
현대 한글 11,172자 전체를 지원할 필요는 없으며, 이를 후속 작업이나 완료 조건으로 두지 않는다.**
기존 선별 글자와 기호는 모두 보존한다. 조합형 입력의 구현·검증은 이 2,350자를 대상으로
진행하며, 중간 조합 표시·편집·확정·저장·재로드는 별도 구현해야 한다.
범위 근거: [Unicode Korean FAQ](https://www.unicode.org/faq/korean.html),
[KS X 1001 2,350자 설명](https://www.unicode.org/L2/L2017/17248-hangul-cmts.pdf).

## 표현과 메모리

- 기존 코드 991개와 그 순서는 바꾸지 않는다. 모든 기존 글리프의 **22바이트 전체**를 보존한다.
  의미가 미확정인 17개 기호도 삭제하거나 일반 문자로 바꾸지 않는다.
- 추가 글자는 Unicode 순으로 배치한다. 코드 공간은 `F040..F7FC`, 각 lead의
  trail `40..FC`에서 `7F` 제외(188개)다. 실제 추가 1,438개만 유효하다.
  기존 두 바이트 이름 형식에 NUL을 끼워 넣지 않는다. 이 코드 공간은 현재 확인한
  DG/general 2-byte 소비자용 개발 사양이며, 전체 미확인 텍스트의 충돌 없음 증거는 아니다.
- 기존 Gulim 2.21, face 0의 내장 12px 비트맵을 새 글자에 사용한다.
  글자 정체성은 검수 문자표, 래스터화는 `match_gulim.render_rows`로 분리한다.
  폰트 해시가 바뀌면 중단하며, 다른 글꼴은 검토된 프로필을 추가해야 한다.
  모든 요구 한글의 cmap 존재, 비어 있지 않음, 12×11 경계 내 잉크를 검사한다.
- 각 글리프를 세로 3/4/4행으로 나누어 동일한 묶음을 공유한다.
  글리프당 u32 인덱스 하나가 세 사전 항목을 선택한다. 현재 인덱스 비트 수는 9/10/8.
  행은 상위 12비트와 하위 nibble(0 또는 F) 플래그를 합친 13비트다.
  화면에 사용하지 않는 하위 비트까지 무손실로 복원한다.
- 새 코드·사전·인덱스·scratch 모두 EXE 논리 파일 `[0x98D38,0x9E278)` 안에 들어간다.
  대응 RAM은 `[0x80128D38,0x8012E278)`이다. ISO LBA/raw sector 좌표는 빌드 보고서에 별도 기록한다.
  전체 21,824바이트 중 21,055바이트 사용, 769바이트 여유. 추가 상주 RAM은 0.
- 388바이트 MIPS I 공급 루틴이 요청 글리프를 같은 영역의 22바이트 scratch에 복원한다.
  기존 렌더러가 이를 즉시 66바이트 4bpp로 변환한 뒤 기존 21개 순환 버퍼로 GPU에 전달한다.
  GPU에 scratch 포인터를 직접 주지 않으므로 다음 글자의 복원으로 GPU 자료가 바뀌지 않는다.
  원래 sentinel 역시 공유 쓰기 상태였으며 새 공급자는 재진입 안전성을 추가로 보장하지 않는다.

생 비트맵으로 2,350자를 상주시킬 경우 한글만 51,700바이트가 필요하다.
EXE/overlay/heap를 이동시키는 대신 기존 전용 영역 내 무손실 사전 방식을 채택했다.
폰트 영역 밖의 빈 것처럼 보이는 RAM이나 EXE padding을 확보 공간으로 사용하지 않는다.

## 후크와 빌드

후크는 EXE 논리 `0x157F0`의 16바이트, RAM `0x800A57F0`이다.
원본 바이트를 확인하고 공급 루틴으로 점프한다. 기존 검색·주소 계산을 대체하고
RAM `0x800A5870`의 원래 변환 단계로 돌아온다. live-in은 기존 frame `sp+0x3e`의 코드,
live-out은 `sp+0x24`의 인덱스와 `sp+0x30`의 글리프 주소다.
SP/GP/RA와 callee-saved 레지스터를 유지하고 caller-saved 및 HI/LO를 사용한다.
분기 delay는 NOP, load delay는 독립 명령으로 검증한다.

LLVM 23.1.2의 MIPS I assembler와 decoder, 독립 Capstone 최종 명령 해석,
분기 목적지/지연 슬롯/ELF relocation 검사 및 재어셈블 바이트 일치를 사용한다.
LLVM disassembler와 parser의 숫자 branch displacement 표기 차이는
Capstone이 해석한 실제 목적지의 로컬 label로 정규화한다.
이 검사는 생성한 명령의 검증이며 모든 원본 실행 코드의 해석 완료 주장이 아니다.

```sh
python3 -m pip install -r requirements-font.txt
# LLVM 23.1.2 llvm-mc/llvm-objcopy를 PATH 또는 LLVM_BIN으로 제공
python3 tools/dg_build.py --expand-font --alignment-repair --output work/build/font-expanded-final
python3 tools/font_cpu_verify.py work/build/font-expanded-final
```

대사는 기존 `dg_export.py`로 내보내고 Unicode를 편집한 후 같은 명령에 `--edits`를 준다.
`--expand-font`가 없으면 기존 991칸 공급 범위를 계속 사용한다. 길이·제어 위치 보존
정책은 동일하다. 지원하지 않는 글자, 슬롯 초과, 제어 손실은 빌드를 중단한다.
확장 공급자는 `tools/font_expand.py`, 실제 MIPS 소스는 `tools/font_provider.s`다.
기존 `tools/build.py`는 정렬 수정 전용으로 유지한다.

최종 쓰기는 기존 `dg_build.sector_plan`을 사용한다. 원본 해시/바이트, 중복 writer,
Form 1 EDC/ECC, 전체 sector diff, 파일시스템 불변, EXE/DG/MAPHEAD 재추출을 검사한다.
루트 ISO와 BIOS는 바꾸지 않는다. 출력 및 폰트 자원은 `work/` 아래 로컬 파일이다.

## 검증과 한계

전체 2,430개에 대해 독립 정적 복원 22바이트 일치와 실제 공급 MIPS + 기존 렌더러의
66바이트 4bpp 결과를 검사한다. 미할당/부적합 코드 7개는 기존 대체 글꼴을 반환한다.
`FFFF`는 기존 기호 코드이므로 미등록 코드 시험값으로 사용할 수 없음을 확인했다.
이를 포함한 모든 기존 코드 보존은 전수 검사에 포함된다.
Unicorn 2.1.4 함수 실행은 PS1 GPU/실제 R3000A load delay 증거가 아니며 게임 검증을 별도로 한다.

28개 자동 테스트에는 압축 경계, 잘못된 행 입력 거부, 코드 trail 경계와 기존 DG 정책을 포함한다.
게임 검증의 정확한 산출물과 범위는 `docs/current.md` 및 런타임 evidence에 기록한다.
폰트 확장은 조합 입력 UI·메모리카드 저장 검증·번역 개선의 완료를 뜻하지 않는다.
